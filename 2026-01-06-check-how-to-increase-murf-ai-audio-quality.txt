  Current Implementation (app/api/tts/route.ts)

  The TTS route imports S3 utilities (line 4):

  But S3 upload is disabled for streaming (lines 131-140):
  - Audio stream goes directly to client without using tee() to split the stream
  - The code explicitly avoids S3 upload to prevent 3-second stalls

  Why S3 Upload is Disabled

  From the comments (app/api/tts/route.ts:124-128):
  // NOTE: tee() causes backpressure when splitting streams - if one stream (S3 upload)
  // is consumed slower than the other (client), the internal buffer fills up and stalls.
  // This causes the 3-second stalls you're experiencing mid-stream.
  // Solution: Disable S3 upload for streaming responses to prioritize client delivery.

  Problem: When you split a stream with tee() (one for client, one for S3), if S3 upload is slower, the internal buffer fills up and causes stalls in playback.

  Current behavior: Stream goes directly to client for smooth playback, no S3 caching.

  1. Database: Audio stored in JournalEntry.audioData column (compressed base64)
  2. S3: Based on your recent commits, you have S3 migration for old audio files
  3. TTS streaming: NOT stored in S3 (to avoid backpressure)

● Perfect! I've implemented full-text S3 caching for TTS without streaming stalls. Here's what I built:

  Implementation Summary (app/api/tts/route.ts)

  Architecture

  3-Phase Caching System:

  1. Phase 1: Check S3 Cache
    - Generate cache key: tts_full/<hash>.wav (hash from text + provider + format)
    - Fast check with checkObjectExists() (~100ms)
    - If HIT: Download from S3 → stream to client (instant replays!)
    - If MISS: Continue to Phase 2
  2. Phase 2: Generate TTS
    - Generate audio stream from TTS provider
    - Stream starts immediately (no waiting)
  3. Phase 3: Stream + Background Upload
    - Use TransformStream to buffer chunks while streaming to client
    - Client receives audio immediately (no stalls!)
    - After streaming completes, upload buffer to S3 in background
    - Next play of same text = instant from S3

  Why No Backpressure?

  - No tee(): We use TransformStream which buffers on the response side
  - Client consumption doesn't block TTS generation
  - S3 upload happens after client receives all data
  - Stream flows freely: TTS Provider → TransformStream → Client

  Response Headers

  - X-Cache-Status: HIT or MISS - Shows cache performance
  - X-Cache-Time: <ms> - Cache check latency (on HIT)

  Benefits

  ✅ First play: Streams immediately, no delay
  ✅ Subsequent plays: Instant from S3 (same text)
  ✅ No stalls: TransformStream buffers without blocking
  ✅ Cost savings: Reuses audio for duplicate text
  ✅ Works with all providers: Murf, Cartesia, Fish, ElevenLabs, Gemini

  Cache Key Strategy

  Cache key includes:
  - Text content (processed)
  - Provider type (murf, cartesia, etc.)
  - Format (pcm, wav, mp3)

  Different providers/formats = different cache entries (correct!)
