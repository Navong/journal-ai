  Audio Storage Format in Database

  In Database (PostgreSQL)

  audioData String? @map("audio_data")
  // Stored as: Base64-encoded string

  Format: Base64 string (text representation of the binary WAV file)
  - Database type: String (PostgreSQL TEXT column)
  - Size: ~6.4MB as base64 text (6728KB you saw in logs)
  - Actual content: WAV file encoded as base64

  When Retrieved (Streaming Mode)

  // API decodes base64 → binary
  const binaryString = atob(entry.audioData); // Decode base64
  const bytes = new Uint8Array(binaryString.length); // Convert to binary
  // Returns: Uint8Array containing binary WAV file

  Format: Uint8Array (binary WAV file)
  - Size: ~4.8MB binary (75% of base64 size due to base64 overhead)
  - Content: Complete WAV file (RIFF header + PCM audio data)

  Complete Flow

  1. Generated by Cartesia
     ↓ Binary WAV stream (Uint8Array chunks)

  2. Converted to base64 for storage
     ↓ Base64 string (~6.4MB text)

  3. Stored in PostgreSQL
     ↓ String column "audio_data"

  4. Retrieved from database
     ↓ Base64 string (~6.4MB)

  5. Decoded by API (atob)
     ↓ Binary WAV (Uint8Array ~4.8MB)

  6. Streamed to client
     ↓ ReadableStream<Uint8Array>

  7. Decoded by Web Audio API
     ↓ AudioBuffer (raw PCM samples)

  Answer: In the database it's stored as base64 string, but when you fetch it with streaming=true, the API decodes it back to binary WAV (Uint8Array) before sending it to the client.

  S3 Streaming - Would It Be Faster?

  Potential Improvements with S3

  Yes, S3 could be faster:

  1. Direct Binary Storage (no base64 overhead)
    - Current: Store as base64 → decode on API → stream
    - S3: Store as binary → stream directly
    - Saves: ~100-200ms (base64 decode time)
  2. CDN/Edge Delivery (with CloudFront)
    - Current: Supabase (single region, likely Singapore based on your AWS region)
    - S3 + CloudFront: Edge locations worldwide
    - Saves: Potentially 500ms-1s for distant users
  3. No API Middleman
    - Current: Client → API → Database → API → Client
    - S3: Client → S3 directly (signed URL)
    - Saves: ~100-300ms (API processing overhead)
  4. Optimized for File Delivery
    - S3 is purpose-built for serving files
    - Better HTTP/2 streaming support
    - Better caching headers

  Expected Performance with S3 + CloudFront

  Current: 1.4s download, 0.5s to playback
  S3:      0.5-0.8s download, 0.3s to playback (50% faster!)

  Trade-offs

  | Factor            | Database (Current) | S3 + CloudFront                                  |
  |-------------------|--------------------|--------------------------------------------------|
  | Speed             | 1.4s download      | 0.5-0.8s download ✅                             |
  | Playback start    | 0.5s               | 0.3s ✅                                          |

  | Caching           | Database cache     | CDN cache (better) ✅                            |
  | Cross-device sync | Built-in           | Need to manage URLs                              |
